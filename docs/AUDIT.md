# Разбор требований и вопросы аудитора

Документ помогает разобраться в решении и повторить объяснение своими словами. Он описывает реализованное поведение и проверяемые границы; угадать все будущие вопросы аудитора невозможно.

## Что происходит после «Предложить палитры»?

Браузер берёт текст формы и, если уже накоплено три применения, вычисленное предпочтение. Он отправляет JSON на `/api/suggest-palette`, отключает кнопку и показывает состояние загрузки. Обработчик проверяет тип содержимого, размер, JSON и диапазоны. Клиент выбирает mock, если не задан URL; иначе вызывает настроенный LLM. Оба пути проходят `Normalize`: проверяются пять цветов, описания, число вариантов и контраст. Возвращённые данные строят карточки через безопасный `textContent`. Нажатие «Применить» меняет CSS-переменные и сохраняет выбор.

## Почему mock не является «настоящим ИИ»?

Он так и обозначен в ответе и интерфейсе. Это предсказуемый локальный набор для демонстрации без инфраструктуры. Настоящий режим делает HTTP-запрос к настроенной модели. Сервис не выдаёт mock за успешный ответ удалённого LLM после ошибки: настроенный недоступный LLM даёт 503.

## Как считается контраст?

Каждый sRGB-канал переводится из диапазона 0–255 в 0–1. Значения до 0,04045 делятся на 12,92; остальные проходят `((c + 0,055) / 1,055)^2,4`. Относительная яркость равна `0,2126R + 0,7152G + 0,0722B`. Отношение — `(светлая + 0,05) / (тёмная + 0,05)`. Белый/чёрный дают 21:1, одинаковые цвета — 1:1. Требование обычного текста — минимум 4,5:1.

## Что делаем с плохой палитрой?

Неправильный формат цвета, отсутствие описаний, неверное число вариантов и одинаковые названия отклоняют ответ LLM. Низкий контраст при корректных цветах исправляет только цвет текста: выбирается чёрный или белый с большим отношением. Декоративный основной цвет остаётся, а подпись кнопки получает отдельный чёрный/белый цвет. Ровно один флаг `recommended` выставляется после нормализации. Если модель дала несколько флагов, сохраняется первый; если ни одного — выбирается первый вариант.

## Почему тема переживает перезагрузку?

После применения в `localStorage` записывается проверенный объект палитры. При загрузке скрипт читает его, повторно проверяет и применяет переменные корневого элемента. Сломанный JSON, неожиданный объект или опасное значение цвета приводят к исходной теме. Запрет хранилища не мешает работе текущей страницы.

## Как устроена память стиля?

История содержит последние 30 основных цветов, а не весь текст пользователя. После третьего выбора каждый цвет переводится в HSL. Тон усредняется по синусу/косинусу, светлота — обычным средним. При взаимном погашении направлений тон берётся из последнего выбора. Средние значения видны пользователю, отправляются в API и проверяются сервером. LLM получает их в промпте; mock меняет основной цвет по этим же значениям. Это простая персонализация, а не обучение весов модели.

## Что будет, если LLM зависнет или вернёт HTML?

Ограничение контекста и HTTP-клиента — 10 секунд. Контекст HTTP-запроса пользователя также передаётся дальше: отмена не должна продолжать ненужный запрос. Ответ больше 128 КиБ, неверный HTTP-статус, HTML вместо JSON и ошибки схемы дают управляемую ошибку. При недоступности API отвечает 503, при испорченном ответе — 500; текст upstream-ошибки и ключ наружу не передаются. Одновременно допускаются 8 реальных запросов палитр; следующий получает 503. Браузер восстанавливает кнопку; готовые темы, генератор и ранее показанный баннер остаются доступны.

## Зачем читать URL и модель из окружения?

Чтобы код не зависел от конкретного компьютера и поставщика, а секреты не попадали в репозиторий. Пустой URL означает mock, даже если имя модели уже задано. URL без имени модели — ошибка конфигурации, которую лучше обнаружить при старте. Разрешены HTTP(S), запрещены логин/пароль в URL, query-параметры и фрагмент. API-ключ передаётся заголовком и не возвращается в сообщения об ошибках.

## Почему не использовать CSS-библиотеку и LLM SDK?

ТЗ ограничивает сервер стандартными пакетами Go. Для фиксированного JSON-вызова достаточно `net/http`, для шаблонов — `html/template`, для статики и встраивания — `io/fs` и `embed`. CSS-сетка и браузерные API уже решают задачу без сборщика и загружаемых ресурсов. Так аудит не зависит от пакетного менеджера и CDN.

## Как защищены формы и шаблоны?

Формы ограничены 64 КиБ; генератор отдельно ограничивает текст и рисунок. Шрифт выбирается по разрешённому имени, а не пути пользователя. `html/template` экранирует текст в форме и выводе, а JavaScript не вставляет ответы модели через `innerHTML`. Цвета — только шесть шестнадцатеричных цифр. Заголовки CSP и `nosniff` дополняют эти меры. JSON-эндпойнт требует `application/json`; CORS не открывается.

## Почему `<pre>` и моноширинный шрифт?

Пробелы — часть рисунка. Обычный HTML сворачивает их, а пропорциональный шрифт даёт символам разную ширину. `<pre>` с `white-space: pre`, фиксированной шириной знаков и прокруткой сохраняет исходные строки даже на узком экране. Область получает фокус, чтобы её можно было прокручивать с клавиатуры.

## Какие ограничения честно остаются?

Контраст проверяется математически, но удобство интерфейса и совместимость всех версий браузеров требуют ручной проверки. Имитационные HTTP-серверы проверяют оба протокола и отказы, а качество реального текста/палитр зависит от выбранной модели. Нет обещания абсолютной отказоустойчивости при неограниченном трафике. Нет авторизации, базы данных и серверного хранения пользовательских тем: они здесь не требуются.

## Что проверяют тесты, а что нужно показать руками?

Автоматически проверяются формулы, mock, схемы, протоколы, отмена, повреждённые ответы, формы, ограничения и параллельные запросы. JavaScript-тесты проверяют сохранённые значения, цвет кнопок и круговое среднее. В браузере следует показать видимость фокуса, отсутствие горизонтального переполнения страницы, применение/восстановление темы, состояние загрузки и сообщения об отказе. Наличие тестового файла само по себе не доказывает успешный запуск — смотрите фактический отчёт CI и `VERIFICATION.md`.
